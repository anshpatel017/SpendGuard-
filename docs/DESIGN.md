# Design Document

## 1. Problem

Organizations lose an estimated ~5% of annual revenue to occupational fraud, with procurement and billing schemes among the most damaging categories. Four things make this hard to fix:

1. **Audits do not scale.** Human auditors manually sample 1-5% of transactions. Over 95% of spend is never examined.
2. **Rules alone fail.** Simple rule engines catch exact duplicates but miss fuzzy ones ("ACME Pvt Ltd" vs "Acme Private Limited"), and they emit so many false positives that auditors learn to ignore them.
3. **Detection is not the bottleneck — investigation is.** Even once a transaction is flagged, a human spends 30-45 minutes pulling vendor history, comparing similar invoices, checking policy, and writing the finding. This per-case cost is why alert queues sit unresolved.
4. **Existing AI audit tools are closed, enterprise-priced, and cloud-hosted.** Financial data must leave the organization to use them, which many organizations legally cannot do. There is no open, locally-runnable equivalent for SMEs, colleges, or public bodies.

**Research question:** Can a fully local, open-source multi-agent system audit 100% of transactions, autonomously investigate prioritized flags, and produce evidence-cited audit notes with measurably high precision and near-zero fabricated citations?

---

## 2. Design goals

| Goal | Meaning |
|---|---|
| **G1 — Complete coverage** | Every transaction row is scored by every applicable detector. No sampling at the detection layer. |
| **G2 — Finished output, not a score** | The unit of output is an investigated case file, not a risk number. |
| **G3 — Verifiable evidence** | Every claim in an audit note points to specific transaction rows that a machine re-checks. |
| **G4 — Measured hallucination** | Citation validity is a reported metric with a target, not an unquantified risk. |
| **G5 — Fully local** | No data leaves the deployment. No paid API in the runtime path. |
| **G6 — Reproducible evaluation** | Ground truth is generated by a scripted, seeded injection harness so results can be reproduced exactly. |
| **G7 — Actionable** | The auditor can work the queue — review, confirm, dismiss, annotate — not just read it. |

## 3. What the system does

```
Procurement CSV
      |
      v   ingest - clean - normalize vendors
DuckDB `transactions`  (every row has a row_id)
      |
      v   D1 - D2 - D3 - D4  run over 100% of rows
Cases  (anomaly groups, scored and ranked by severity)
      |
      v   top-N by severity
Investigator Agent  (tool loop over a local LLM)
      |   queries data, profiles vendors, looks up policy, computes
      v
Draft audit note  (structured JSON, every claim cites row_ids)
      |
      v   Verifier Agent: re-fetch every cited row, confirm support
Released audit note  +  verification badge
      |
      v
Dashboard  (queue, evidence, traces, case state workflow)
```

## 4. Core design decisions and rationale

### 4.1 The object we detect on is a transaction record

We are not performing invoice-to-payment three-way matching.

- D1 detects **duplicate transaction records** — the same obligation appearing twice in the data — not confirmed double-disbursement.
- On a purchase-order dataset, D1 finds duplicate POs. On a payment dataset, the identical logic finds duplicate payments. Only the object changes.

**Wording used everywhere:** "duplicate transaction records (POs or payments, depending on the source system)".

**Limitation stated in the report:** true duplicate-payment confirmation requires invoice-to-payment reconciliation, which the available public datasets do not contain.

### 4.2 A case is an anomaly group, not a row

| Anomaly | Case shape |
|---|---|
| Duplicate pair | 1 case, 2 row_ids |
| Split purchase of 5 POs | 1 case, 5 row_ids |
| Price inflation on a line item | 1 case, 1 row_id |
| Vendor red flag | 1 case, N row_ids (that vendor's transactions) |

Primary metrics are computed **per case**; per-row metrics are reported as a secondary table because the two answer different questions.

### 4.3 The agent is a filter as well as a reporter

The Investigator emits one of three verdicts:

- `likely_true_positive` — full finding plus a recommended action
- `likely_false_positive` — short dismissal note explaining why (e.g. "vendor has a legitimate recurring monthly billing pattern, rows 1102-2840")
- `inconclusive` — what it found and what a human should check

This is deliberate: it is what reduces the false-positive burden that makes rule engines unusable in practice.

**The agent never deletes or auto-closes anything.** It recommends; the human decides. A dismissed case stays in the queue under a "Dismissed by agent" filter so the decision remains auditable.

### 4.4 Detection is 100%; investigation is top-N by severity

| Layer | Coverage |
|---|---|
| Detection | Every row, always. This is the "100%" claim and it is true. |
| Investigation | Top-N cases by severity. N is configurable — a small N for a demo run, a larger N for an evaluation run. Remaining cases sit in the queue with detector output only, marked *not yet investigated*. |

The dashboard states this honestly: *"34 cases flagged · 20 investigated · 14 queued."*

**Claim wording:** "Detects across 100% of transactions, then autonomously investigates prioritized cases." Never "investigates every flagged case."

**Rationale, if challenged:** investigation is LLM-bound at roughly 30-60 seconds per case on commodity GPU hardware, so cases are prioritized by severity — exactly as a real audit team triages. The narrow claim is stronger than the overclaim.

### 4.5 The agent loop is hand-written, not a framework

A plain Python while-loop: call the model with the case and tool definitions, parse the tool call, execute the tool, feed the result back, repeat to a step limit, emit a structured note.

Frameworks place hundreds of lines of abstraction between the team and the agent's actual behaviour. Every step here must be explainable and debuggable. Migrating to a framework later is straightforward; starting with one costs understanding.

### 4.6 Two databases, chosen by access pattern

| Store | Holds | Why |
|---|---|---|
| **DuckDB** | `transactions`, detector output, evaluation results | Columnar/OLAP. Detectors run heavy aggregate queries over hundreds of thousands of rows. Read-only at serving time. |
| **PostgreSQL** | `cases`, case status, reviewer notes, audit notes, agent traces, run history | Transactional/OLTP. Case state changes are small concurrent writes from a web API — precisely what DuckDB, as a single-writer embedded engine, handles badly. |

This is the standard OLTP/OLAP separation. It also removes the write-lock contention a single-DuckDB design would hit as soon as the dashboard and a batch run overlap.

### 4.7 Vendor normalization is the foundation

Every detector depends on collapsing vendor name variants into a stable key. Legal suffixes are stripped, punctuation dropped, tokens sorted so word order does not matter.

Known trade-off: aggressive normalization can collapse genuinely different vendors sharing a stem. The normalized key is therefore used for **blocking** (generating candidates), with a second similarity check on the raw name before two records are called duplicates.

### 4.8 The procurement policy is authored by the team, and we say so

Public datasets do not ship with the issuing organization's internal policy document. A representative policy is authored in `policy/`, with clauses derived from India's General Financial Rules (GFR) 2017 and CVC procurement guidelines, optionally referencing the US FAR micro-purchase threshold for US data.

Minimum clauses: approval thresholds by value; prohibition of splitting purchases to avoid thresholds; duplicate payment prevention and recovery; vendor onboarding requirements; price reasonableness / market rate comparison.

The split-purchase threshold is a **config value**, and the policy document states the same figure, so the agent's citation and the detector's behaviour never disagree.

### 4.9 Ground truth is injected, because it does not exist

No public procurement dataset ships with fraud labels. Realistic, parameterized anomalies are injected into real data with fixed seeds. This is the only way to report precision and recall an examiner can trust. Full specification in [EVALUATION.md](EVALUATION.md).

## 5. Severity model

Two distinct numbers, deliberately named differently to avoid confusion.

**`detector_score`** — float 0-1, produced by the detector. Detector confidence only. Each detector normalizes its own internal statistic: Splink match probability, robust z-score through a logistic, inverted Benford chi-square p-value, split-purchase proximity to threshold.

**`severity`** — float 0-100 plus a band, assigned in two stages:

- **Stage 1, at case creation:**
  `severity_prelim = 100 * detector_score * amount_weight`
  where `amount_weight = log1p(amount_at_risk) / log1p(reference_amount)`.
  This is what the top-N investigation queue is ordered by.
- **Stage 2, after investigation:** the agent may adjust the band based on its verdict — `likely_false_positive` drops to Low, `inconclusive` caps at Medium, `likely_true_positive` keeps the preliminary band.

**Bands:** High >= 66 · Medium 33-65 · Low < 33.

## 6. Human in the loop

Minimal case state management is **in scope**:

- Per case: `New -> Under Review -> Confirmed -> Dismissed`
- Plus a free-text reviewer note
- Stored in PostgreSQL

Out of scope: login, auth, multi-user, retraining from feedback, email or ticket integration.

**Rationale:** a read-only dashboard is a report viewer; a queue you can act in is a tool. The cost is small and it makes the demonstrated workflow complete end to end.

---

## 7. Out of scope

- Malware / antivirus detection
- Hand-written expert rules — all detection is data-driven
- Any paid cloud LLM API in the runtime system
- Authentication, RBAC, multi-tenancy, production deployment concerns
- Invoice-to-payment three-way matching
